# 笔记本：占卜笔记 + 用户画像

**让占卜师记得住这个人。** 只有注册用户有笔记本。

用户来占卜，聊的是自己的处境。下一次再来，如果占卜师什么都不记得，从头再问一遍，
这个产品就只是个抽牌工具。笔记本就是那份「记得住」。

一场占卜结束后，**记忆 Agent** 读完整场对话，写下两样东西：

| | 是什么 | 怎么变 | 像什么 |
|---|---|---|---|
| **占卜笔记** | 这一场发生了什么：问了什么、抽了什么牌、占卜师怎么说、用户怎么回 | **一场一条，往后追加** | 日记本，一天一页，写完翻页 |
| **用户画像** | 这个人是谁：生活近况、身边的人和事、对他的理解、他喜欢怎么被对待 | **一人一份，反复修改** | 名片，内容一直在更新，但永远只有一张 |

两样东西由**同一次模型调用**一起产出：模型先看到这个人当前的画像，再决定这一场要改哪几项。

> 为什么是两样：笔记回答「上次那件事后来怎么样了」，画像回答「这个人是谁」。
> 前者必须一场一条留着不动（改了就是篡改历史），后者必须能随时推翻重写（人是会变的）。
> 一样东西满足不了两个要求。

---

## 1. 什么时候写

用户离开对话（切对话 / 开新对话 / 退出登录 / 关网页）→ 登记任务 → **12 小时后**生成。

- 要抽过牌、有对话内容才登记。
- 同一场对话之后又回来接着聊，下次离开重新登记，到点后**整条重写**那一条笔记
  （不是在后面接一段）。笔记本里这场对话永远只占一条，位置按第一次写入排。
- 游客离场不登记、到点的旧任务只删不生成、占卜师翻笔记本时直接告诉它没有。
  连带：每日一签的心灵奇旅会摘最近的笔记，游客那一块恒为空，只按抽签记录写。

---

## 2. 占卜笔记

四个字段，模型写：

| 字段 | 写什么 |
|---|---|
| `question` | 用户想问什么，以及他说到的相关处境 |
| `cards_drawn` | 这场抽到的所有牌 |
| `summary` | 占卜记录，不超过 300 字 |
| `user_feedback` | 用户对解读的回应：认了什么、否了什么、打算怎么做 |

占卜时间不让模型写（它不知道今天几号），由代码按对话的开始 / 结束时间记。

**两条硬规矩：**

1. **字段写不满是正常的，不许为了填满而编。** 用户没说处境就空着，没表态就空着，
   占卜师没解读的牌不替它解读。宁可空，不要编。
2. **不变的信息不记。** 用户资料（昵称、性别、生日、出生地）和本命星盘都另有唯一出处，
   抄进笔记只会和原件对不上。占卜师翻出来的旧笔记也不许抄进新的一条。

---

## 3. 用户画像

四项，各是一段话：

| 字段 | 写什么 |
|---|---|
| `recent` | 生活近况：职业 / 学业、感情、家庭、居住 |
| `people_and_events` | 近期重要的人、关系、正在经历的事和最新进展 |
| `understanding` | 对这个人的累积认识：在意什么、怎么做决定、什么让他难受、什么方法对他管用 |
| `preferences` | 交流偏好：希望怎么被回应，不喜欢什么表达，哪里不能碰 |

**改的规则只有三条：**

1. **只回这一场要改的项。** 没回的原样留着。这一场没什么可记的（多数场次都是），就一项都不回。
2. **回的那项是覆盖写**——写出来的是这一项改完之后的完整内容，不是补丁片段。
   要在原有内容上加，就把加完的整段写出来；过时了就直接写新的；要删掉就写空。
3. **不许写时间。** 每项带一个 `confirmed_at`，是这一项最后一次被写的那场对话的结束时间，
   由代码记。用来判断这条还新不新——半年前记的「在上海做设计」可能已经过期了。

```json
{
  "recent":            {"text": "在上海做设计",  "confirmed_at": "2026-09-18T12:00:00"},
  "people_and_events": {"text": "男友在杭州",    "confirmed_at": "2026-09-20T09:00:00"},
  "understanding":     {"text": "",             "confirmed_at": ""},
  "preferences":       {"text": "",             "confirmed_at": ""}
}
```

**画像的边界：**

- 稳定资料（昵称 / 性别 / 生日…）和本命星盘不进画像，理由同笔记。
- 只写有依据的。占卜师的解读是它的推测，用户没认领的说法不算事实。
- 用户说得少、没给反馈，这场就别更新。

---

## 4. 画像怎么被读

`context_service.build_portrait_context()` 每轮读画像，渲染成 `# <用户画像>` 块，
接在 `# <用户资料>` 后面，**开场和解读两个相位都无条件带上**——
「被记住」不取决于模型想不想调工具。

块里只列写过的项，每项带上次记下的日期；一项都没写过就是一行「还没有形成印象。」
（四个空字段的骨架对模型没有用处）。怎么用这一块（这是过去的印象、不要拿它给人下定义、
不要复述、空着是正常的）写在 `prompts/portrait_usage.md`，跟着块一起发，管理页可改。

游客没有笔记本，整块连同规则都不出现。

注入长度不另做限长：每项 500 字的上限已经由 `notebook_system.md` 管着（写侧），
满打满算 4 项约 2000 字；再在读侧截一刀只会把话截断在半句上。

工具 `read_divination_notes` 的职责是**翻出以前每一场占卜的记录**——
「这个人是谁」已经由画像块每轮带着，不必再靠它。

---

## 5. 模型看到的是什么

整场对话原样转成文字（`build_transcript`），**只换格式，不丢内容**：
每条记录按发生顺序转一段，JSON 换成「标签：值」，工具名换成动作，
用户看不见的内容标「后台」，跨天插日期行。
不写的只有纯管道信息：调用 id、`success=true`、和正文重复的展示字段。

---

## 6. 出错了怎么办

**模型回来的不是合格 JSON**（解析不了、不是对象、字段类型不对、根本没有笔记）→
当场重摇，最多 3 次。

**3 次都不合格，或者模型服务报错** → 直接放弃，**不写假笔记**。
任务记下错误删掉，用户下次离开这场对话时会重新登记。

**内容本身不做检查。** 提示词里写「每项不超过 500 字」，模型写长了照收。
硬限长 + 超限重摇的代价不对等：一个 501 字的画像字段会把同一次产出的那条合格笔记
一起丢掉，再跑一整场对话稿。而且字段是覆盖写、模型每次都看得见当前画像，
不是越滚越长的结构。

---

## 7. 存在哪

```
backend/data/notebooks/
  note_<user_id>.log        占卜笔记，一个 JSON 数组，一场一条
  portrait_<user_id>.json   用户画像，一人一份
```

游客登出时两个文件一起删。老用户从空画像开始自然积累，没有做历史笔记回填。

---

## 8. 代码在哪

| 文件 | 管什么 |
|---|---|
| `services/notebook_service.py` | 全部逻辑：对话稿转写、调模型、笔记追加、画像合并、读写文件 |
| `prompts/notebook_system.md` | 记忆 Agent 的提示词（笔记 + 画像的全部要求） |
| `services/context_service.py` | 读侧：画像渲染成块 + 注入两个相位的提示词 |
| `prompts/portrait_usage.md` | 画像块跟着发的使用规则（管理页可改） |
| `services/notebook_task_scheduler.py` | 离场登记任务、到点生成 |
| `routers/conversations.py` `/exit` | 离场触发点 |
| `services/turn_service.py` `_read_notes` | `read_divination_notes` 工具的实现 |
| `services/llm/agent_config.py` | 记忆 Agent 用哪个 provider / 模型 |

**画像的字段结构在代码里只声明一次**（`notebook_service._PortraitPatch`）：
画像文件的骨架、合并时保留哪些字段、模型返回的 JSON 收下哪些字段，全从它推出来。
提示词里还有一份（表格 + JSON 示例），两份必须对得上——
`test_prompt_and_code_agree_on_the_portrait_fields` 会比对，漏改哪边都会红。
（漏改本来是静默失败：不抛异常、测试全绿、日志照常打「画像已更新」，几周后才发现那项一直是空的。）
