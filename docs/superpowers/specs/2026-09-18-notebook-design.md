# 笔记本：占卜笔记 + 用户画像

创建：2026-09-18 ｜ 状态：**画像已经写也已经读；笔记由占卜师按需翻**

这条线的唯一入口。笔记本这块要改什么、现在是什么样、还缺什么，看本文就够，不用翻
[多 Agent 架构总纲](2026-07-14-multi-agent-redesign-design.md)。总纲那边只留索引。

**关系环**（占卜结束几天后主动接话）也归在这里：它吃的是笔记本产出的钩子，
没有笔记本就没有关系环。见第 8.4、8.5 节。

---

## 1. 这是什么

**让占卜师记得住这个人。**

用户来占卜，聊的是自己的处境。下一次再来，如果占卜师什么都不记得，从头再问一遍，
这个产品就只是个抽牌工具。笔记本就是那份"记得住"。

一场占卜结束后，一个叫**记忆 Agent** 的模型读完整场对话，写下两样东西：

| | 是什么 | 怎么变 | 像什么 |
|---|---|---|---|
| **占卜笔记** | 这一场发生了什么：问了什么、抽了什么牌、占卜师怎么说、用户怎么回 | **一场一条，往后追加** | 日记本，一天一页，写完翻页 |
| **用户画像** | 这个人是谁：生活近况、身边的人和事、对他的理解、他喜欢怎么被对待 | **一人一份，反复修改** | 名片，内容一直在更新，但永远只有一张 |

两样东西由**同一次模型调用**一起产出：模型先看到这个人当前的画像，再决定这一场要改哪几项。

> 为什么是两样：笔记回答"上次那件事后来怎么样了"，画像回答"这个人是谁"。
> 前者必须一场一条留着不动（改了就是篡改历史），后者必须能随时推翻重写（人是会变的）。
> 一样东西满足不了两个要求。

---

## 2. 什么时候写

用户离开对话（切对话 / 开新对话 / 退出登录 / 关网页）→ 登记一个任务 → **12 小时后**生成。

- 要抽过牌、有对话内容才登记。
- 同一场对话之后又回来接着聊，下次离开重新登记，到点后**整条重写**那一条笔记（不是在后面接一段）。
  笔记本里这场对话永远只占一条，位置按第一次写入排。
- **只有注册用户有笔记本。** 游客离场不登记、到点的旧任务只删不生成、占卜师翻笔记本时直接告诉它没有。
  连带：每日一签的「心灵奇旅」会摘最近的笔记，游客那一块恒为空，只按抽签记录写。已接受。

## 3. 占卜笔记怎么写

四个字段，模型写：

| 字段 | 写什么 |
|---|---|
| `question` | 用户想问什么，以及他说到的相关处境 |
| `cards_drawn` | 这场抽到的所有牌 |
| `summary` | 占卜记录，不超过 300 字 |
| `user_feedback` | 用户对解读的回应：认了什么、否了什么、打算怎么做 |

占卜时间不让模型写（它不知道今天几号），由代码按对话的开始/结束时间记。

**两条硬规矩：**

1. **字段写不满是正常的，不许为了填满而编。** 用户没说处境就空着，没表态就空着，
   占卜师没解读的牌不替它解读。宁可空，不要编。
2. **不变的信息不记。** 用户资料（昵称、性别、生日、出生地）和本命星盘都另有唯一出处，
   抄进笔记只会和原件对不上。占卜师翻出来的旧笔记也不许抄进新的一条。

---

## 4. 用户画像怎么写

四项，各是一段话：

| 字段 | 写什么 |
|---|---|
| `recent` | 生活近况：职业/学业、感情、家庭、居住 |
| `people_and_events` | 近期重要的人、关系、正在经历的事和最新进展 |
| `understanding` | 对这个人的累积认识：在意什么、怎么做决定、什么让他难受、什么方法对他管用 |
| `preferences` | 交流偏好：希望怎么被回应，不喜欢什么表达，哪里不能碰 |

**改的规则只有三条：**

1. **只回这一场要改的项。** 没回的原样留着。这一场没什么可记的（多数场次都是），就一项都不回。
2. **回的那项是覆盖写**——写出来的是这一项改完之后的完整内容，不是补丁片段。
   要在原有内容上加，就把加完的整段写出来；过时了就直接写新的；要删掉就写空。
3. **不许写时间。** 每项带一个 `confirmed_at`，是这一项最后一次被写的那场对话的结束时间，
   由代码记。用来判断这条还新不新——半年前记的"在上海做设计"可能已经过期了。

存出来长这样：

```json
{
  "recent":            {"text": "在上海做设计",  "confirmed_at": "2026-09-18T12:00:00"},
  "people_and_events": {"text": "男友在杭州",    "confirmed_at": "2026-09-20T09:00:00"},
  "understanding":     {"text": "",             "confirmed_at": ""},
  "preferences":       {"text": "",             "confirmed_at": ""}
}
```

**画像的边界：**

- 稳定资料（昵称/性别/生日…）和本命星盘不进画像，理由同笔记。
- 只写有依据的。占卜师的解读是它的推测，用户没认领的说法不算事实。
- 用户说得少、没给反馈，这场就别更新。

> **曾经有过、已经删掉的**：模型原本还要回一个 `confirmed` 标记，说这一项是不是用户亲口
> 确认的，代码据此决定要不要更新时间。删掉的理由：来源的区分已经由字段本身承担了
> （`recent` 本来就只放用户说过的事实，`understanding` 本来就是推断），在字段里再标一次
> 是同一件事做两遍；而且那个标记是块级的，反而让时间对不准。现在时间就是"最后一次被写"。

## 5. 出错了怎么办

**模型回来的不是合格 JSON**（解析不了、不是对象、字段类型不对、根本没有笔记）→ 当场重摇，
最多 3 次。实测 DeepSeek 的 JSON 模式约 1/8 的回复不合格。

**3 次都不合格，或者模型服务报错** → 直接放弃，**不写假笔记**。任务记下错误删掉，
用户下次离开这场对话时会重新登记。

**内容本身不做检查。** 提示词里写"每项不超过 500 字"，模型写长了照收。
曾经做过硬限长 + 超限重摇，代价不对等：一个 501 字的画像字段会把同一次产出的那条合格笔记
一起丢掉，再跑一整场对话稿。而且字段是覆盖写、模型每次都看得见当前画像，不是越滚越长的结构。

## 6. 模型看到的是什么

整场对话原样转成文字（`build_transcript`），**只换格式，不丢内容**：每条记录按发生顺序转一段，
JSON 换成"标签：值"，工具名换成动作，用户看不见的内容标「后台」，跨天插日期行。

不写的只有纯管道信息：调用 id、`success=true`、和正文重复的展示字段。

> 这条是 2026-09-17 改的。此前按"只写用户看得见的事"挑着写，把开场确认的问题、
> 填的资料、星盘、调用原因全丢了——记忆 Agent 因此根本看不到用户的问题和背景。
> 教训：模型少了信息，要修的是那个丢信息的转换步骤，不是在提示词里另外塞一块。

## 8. 还缺什么（待办）

### 8.1 ~~画像只写不读~~　✅ 2026-09-18 做完

`context_service.build_portrait_context()` 每轮读画像，渲染成 `# <用户画像>` 块，接在
`# <用户资料>` 后面，开场和解读两个相位都无条件带上。块里只列写过的项，每项带上次记下的日期；
一项都没写过就是一行「还没有形成印象。」——四个空字段的骨架对模型没有用处。怎么用这一块
（这是过去的印象、不要拿它给人下定义、不要复述、空着是正常的）写在 `prompts/portrait_usage.md`，
跟着块一起发，管理页可改。游客没有笔记本，整块连同规则都不出现，提示词和加这块之前一字不差。

注入长度没有另做限长：每项 500 字的上限已经由 `notebook_system.md` 管着（写侧），
满打满算 4 项 ≈ 2000 字；再在读侧截一刀只会把话截断在半句上。

同一天把工具也摆正了：`read_divination_notebook` → **`read_divination_notes`**，
职责是「翻出以前每一场占卜的记录」——「这个人是谁」已经由画像块每轮带着。
描述改成直接说功能（翻出哪些内容、什么时候调），结果字段 `notebook_count` / `notebook_content`
跟着改成 `note_count` / `notes`，`turn_service._read_notes` 同名。
旧名字没做兼容映射：落库时用过旧名字的只有一场测试会话。

### 8.2 对话稿里有三段注定被忽略的内容

完整星盘数据、占卜师翻出来的整本旧笔记、占卜师的思考（`reasoning`），
都原样写进对话稿，然后提示词再写规则叫模型别记它们——一进一出都在花钱。

星盘尤其该换成一行标记：现在有 `User.natal_chart` 这个唯一出处，
按"不变的信息不重复记"的规矩，不该在每场对话稿里再抄一遍。
动的时候要同时删掉提示词里对应的那几条规则。

### 8.3 生成时机：12 小时 → 静默 30 分钟

`notebook_task_scheduler.py` 仍是 12 小时。改成"最后一条消息之后 30 分钟没续上"，
用户当天回访就能享受到更新后的画像。长会话每 12 轮用户消息追加一次增量更新兜底。

### 8.4 钩子

笔记本再产出第三样东西：**未完结的话题**，一句话 + 日期。

比如用户说"下周要跟她摊牌"，占卜完就走了 —— 这就是一个钩子。只落库，先不消费，
它是下面那件事的原料。

### 8.5 关系环：让占卜师主动回来找你　（依赖 8.4）

**现在是这样：用户离开之后，这个产品就从他的生活里消失了。** 下次想起来才会打开，
中间那几天什么都没有发生。有笔记本也一样 —— 笔记本只是让"他再来的时候"体验更好，
不解决"他想不起来再来"。

要做的是：占卜结束几天之后，占卜师**主动**接上那句没说完的话。
"上周你说要跟她摊牌，后来怎么样了？"

- **问候 Agent**：读钩子，写一句主动接话。
- **什么时候发**：距上次占卜超过 N 天，且有没消费过的钩子。
- **发在哪**（还没定，二选一或者都要）：
  - 主界面上占卜师主动搭话；
  - 或者在旧的那个会话窗口里延时接话。
- **绝对不放在新会话的开场里。** 新会话就是新开场，用户开一场新的占卜，
  是想问一件新的事，不是想被翻旧账。这条和「接场」的原则是同一条：
  老用户认得出来、叫得出昵称，但**不主动提旧话题** —— 旧话题属于关系环，不侵入新会话。

**做之前必须先有 8.4 的钩子字段**，现在还不存在。

> 这块从 2026-07-14 起就只是纸面设计，一行没写，符合当初的决定（本期只出 spec）。
> 之所以拖着，是因为它排在记忆闭环后面：占卜师连"记得住"都还没做到，
> 谈不上"主动回来找你"。

### 8.6 游客仍然看得见 `read_divination_notes`

`gemini_service.tool_names()` 只看会话类型和相位，不看用户类型，游客每场都会调一次、
拿回一句"只对注册用户开放"。要么工具集按用户类型过滤，要么接受这一次往返的浪费。

### 8.7 游客转注册时的资源迁移没有承接方

原来有个 `migrate_notebook()`，零调用（游客转正 `user_id` 不变，用不上），2026-09-18 已删。
将来若改成转正换 `user_id`，笔记 + 画像 + 其他按 `user_id` 存的资源要一起迁，
到时重新设计，不要再留一个没人调的空壳。

## 9. 代码在哪

| 文件 | 管什么 |
|---|---|
| `services/notebook_service.py` | 全部逻辑：对话稿转写、调模型、笔记追加、画像合并、读写文件 |
| `prompts/notebook_system.md` | 记忆 Agent 的提示词（笔记 + 画像的全部要求） |

| `routers/conversations.py` `/exit` | 离场触发点 |
