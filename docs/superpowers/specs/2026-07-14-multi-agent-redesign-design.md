## 1. 背景与动机

当前占卜核心是**单 Agent + 一组提示词**：一个 Gemini Function Calling Agent Loop 承担全部职责（意图识别、澄清、抽牌、星盘、解读、记忆读取）。四个痛点：

1. **关键行为不稳定**——"读笔记本""控制节奏""从虚到实"这些核心设计全靠提示词祈使句，模型时灵时不灵。
2. **提示词过载**——人格、流程、工具、风格混在一个大文件里互相干扰，function calling 准确率被拖累。
3. **新能力塞不下**——实时用户画像、主动问候/每日推送，在单 Agent 架构里无处安放。
4. **记忆能力设计不足**——长期记忆依赖模型主动调工具，是概率事件而非确定行为。

本文档先定义**产品要做什么**（第 2 节），再定义**技术怎么做**（第 3–5 节）。

## 2. 产品层重构（要做什么）

### 2.1 现有工作流拆解

把一场占卜按用户经历的顺序解剖，现状是：

| 幕 | 现在发生什么 | 设计状态 |
|---|---|---|
| ① 进场 | 通用欢迎语，邀请提问 | **空白**——对第 1 次和第 10 次来的人说同一句话 |
| ② 提问 | 预输入（硬编码）或自由输入 | 已设计，不动 |
| ③ 澄清 | 提示词一句"意图模糊时优先澄清" | **半设计**——只澄清"问题"，不读"人" |
| ④ 仪式 | AI 决定牌阵 → 按钮 → 洗牌 → 扇形选牌 | 已设计，产品亮点，不动 |
| ⑤ 解读 | 牌义 → 个性化 → 投射提问 → 叙事串联，从虚到实 | 理念完整，执行靠自觉 |
| ⑥ 反馈 | "解读是否偏离""你想到了哪件事" | 有设计，但反馈信号用完即弃 |
| ⑦ 收尾 | 不存在，对话默默衰减 | **空白** |
| ⑧ 离场后 | 12 小时后定时生成笔记 | 纯归档，用户无感知 |
| ⑨ 回访 | 与新用户零差别 | **空白** |

**结论：会话中段（②④⑤）精心设计，两端（①③⑦⑧⑨）接近裸奔。** 而两端决定关系——产品愿景是"个人专属的情感陪伴"，但当前工作流本质是**单场服务模型**：一锤子买卖做得精致，买卖之间没有关系。

### 2.2 三个视角的断层诊断

**占卜师视角——"读人先于读牌"缺失。** 真实占卜师在洗牌前已完成一半工作：判断来人是求确认还是真迷茫。README 已写出这个洞察（四类用户目标：已有答案求认同 / 辅助决策找理由 / 探索好奇 / 玄学目的，且"目标会在占卜中变化"），**但当前工作流对这个分类零使用**。同一张"恋人逆位"，对求认同者和对找决策理由者，正确策略完全不同。这个判断现在完全悬空。

**心理从业者视角——会谈没有弧线。** 咨询每一节都有结构：开场衔接 → 中段工作 → 收尾整合。用户记住一场体验的方式由峰值与结束决定（峰终定律）；峰值有设计（被命中的瞬间、抽牌仪式），结束是真空。

**C 端产品视角——留存环是断的。** 陪伴型产品的环应是：会话 → 记忆沉淀 → 回访钩子 → 回访触发 → 衔接开场 → 会话。现在五段断了三段：沉淀延迟 12 小时且不保证被使用、回访钩子从未制造、回访触发不存在。**每次回来都要重新自我介绍的产品，谈不上情感依赖。**

### 2.3 重构后的产品定义

从"一场精致的占卜"升级为"**一段被经营的占卜关系**"。

**会话内四幕：**

1. **接场**——认人但不翻旧账。老用户用熟人语气、叫昵称，**不主动提旧话题**（旧话题属于关系环，不侵入新会话）；新用户走现有欢迎引导。
2. **读人**——暗活，用户不可见。在澄清问题的同时判断用户目标与情绪浓度，产出**本场策略单**（含牌阵选型）。澄清预算**最多 1 轮**。
3. **仪式**——现有抽牌流程**原样保留**。
4. **解读**——现有方法论**原样保留**（从虚到实、投射提问、叙事串联、多次抽牌纪律）。

**离场工序（不可见）：** 会话退出/静默超时后，记忆沉淀 + 钩子提取。

> **收尾幕已评估并撤销**：它的三个价值中，回访钩子可由离场工序从对话原文提取（无需台前说出），整合已包含在现有解读收束话术中，而峰终记忆依赖"准确识别用户要走了"——该判断天然不可靠，误判提前收束等于赶客。**不做结束判断、不加结束按钮。**

**关系环（本期只出 spec，不实现）：** 离场 → 记忆沉淀（含钩子）→ 回访触发（主界面或旧会话窗口的主动接话）→ 下一场。

### 2.4 已对齐的产品决策

- **人格 ≠ 功能**。塔罗 / 占星是**功能**（同一个 Agent 都会，入口只决定起手优先级）；人格是同一占卜师的口吻风格变体（温柔型 / 直接型）。README 描述的双人格**在代码中并不存在**——两份提示词的实质差异只有工具优先级顺序。**本期人格单一，结构上留出替换位置。**
- **反馈沉淀只沉淀事实，不沉淀判词**。沉淀 MBTI、职业、感情状态、重大事件等客观画像；**绝不沉淀"准/不准"判词**。用户说"不准"是本场对话内的信号，由解读方法论当场处理（探索落差、坚持牌面立场），**不能因单次反馈就长期扭转话术**——那是占卜方法论的自毁。

## 3. 技术层设计（怎么做）

### 3.1 总体原则

- **纯增量**。现有 `tarot_system.md` / `astrology_system.md` **一字不动，本期不做去重**（两份文件的方法论重复是已知负债，列为后续优化）。所有新增能力以**追加块**形式由 harness 拼装在现有系统提示词之外。
  *（实际落地时此条部分改变：解读相位仍是追加块，但开场相位用的是一份完整独立的
  `opening_system.md`，不叠在塔罗提示词上。两份大提示词本身确实一字未动，去重也确实没做。
  代价是它们里"首次对话先欢迎""参数化澄清"两条指令与开场幕打架，需另注入接场约束压掉——见缺口 2。）*
- **单一台前声音**。只有占卜师 Agent 对用户说话。不引入台前导演层（每轮串行小模型判断）——双概率系统 + 每轮延迟，收益不抵成本。
- **判断力留在台前，产物落到后台**。策略判断由占卜师自己做（它有全部上下文），但产出必须是结构化对象并持久化，而非散落在对话历史里。
- **台后异步**。记忆沉淀不占用户等待时间。
- **不实现**：危机正则、情绪优先铁律、提示词去重、双人格、收尾幕。

### 3.2 架构总览（下图为**实际运行中**的架构，❌ 为未建成部分）

原案是"单一台前 Agent + 提示词追加块"；实际落地是"两个 Agent 分幕接力"。差别见 §3.3。

```
新建塔罗/占星会话 ──► phase="opening"
   │
   ├─[空消息]──► 前置占卜师(OPENING provider) ── 无工具，单次调用 ──► 开场白
   │                拼装: opening_system.md + <入口> + <关系上下文>       (8s 超时 → 模板降级)
   │                          ▲
   │                          └─ 关系上下文 = 昵称 / 来访次数 / 距上次 N 天（一条 SQL，只数塔罗+占星）
   │                             ❌ 画像卡(缺口 1) —— 未建，此处只有次数与间隔，无任何事实记忆
   │
   └─[用户提问]─► 前置占卜师 ── 唯一工具: submit_reading_brief ──┐  0–2 轮叙事性澄清
                     三层守卫: 提示词纪律 / mode=ANY / 兜底翻相位  │
                                                                  ▼ 交单(九字段) → 落库 + phase="reading"
                     ┌────────────── 同轮移交（同一次 SSE 内换提示词与工具集续跑）
                     ▼
              解读占卜师(READING provider)
                 拼装: tarot/astrology_system.md + 用户资料(仅昵称/性别/生日/出生地)
                       + <本场策略单回显> + <接场约束>
                 工具: draw_tarot_cards / get_astrology_chart / request_user_profile /
                       read_divination_notebook / submit_reading_brief(中途改判)

离场(退出 / 12h 后定时) ──► 记忆 Agent(MEMORY provider) ──► {summary, cards_drawn}
                                                  ❌ 画像增量 + 钩子(缺口 5) —— 未建
                                                  ❌ 触发改静默 30min —— 未做，仍 12h
❌ 关系环(缺口 6) —— 未建，且依赖上面两个 ❌
```

**产品要求 → 实际保障者：**

| 产品要求 | 保障者 | 方式 | 状态 |
|---|---|---|---|
| 接场·认人不翻旧账 | 前置 Agent + Harness | 关系上下文块（次数/间隔/昵称）+ 块内明令禁止翻旧账 | ✅ |
| 读人·产出策略单 | 前置 Agent + 新工具 | `opening_system.md` + `submit_reading_brief` | ✅（取值质量见 §5.4） |
| 仪式 | 现状 | 完全不动 | ✅ |
| 解读·方法论 | 解读 Agent | 现有提示词不动 + 策略单回显 + 接场约束 | ✅ |
| 被记住 | — | 原定画像卡每轮常驻注入 | ❌ 仍靠模型主动调 `read_divination_notebook`，依旧是概率事件 |
| 离场沉淀 + 钩子 | — | 原定记忆 Agent 三产物 | ❌ 仍只有会话摘要 |

### 3.3 核心决策：策略单由谁产出（保留为决策记录；实际走了第四条路）

当时的三个候选与结论如下。**实际实现走的是 (b) 的变体**：策略单仍由台前 Agent 经工具落单
（所以 (a)/(c) 的否决理由依然成立），但读人不再由那个"唯一台前 Agent"兼任，
而是拆给一个独立的前置 Agent，用自己的小提示词做完再移交——即分幕接力。
被否决的 (c) 与此有本质区别：(c) 是每轮都跑第二个模型，分幕接力是每场只在开场跑一次，
任意时刻仍只有一个声音在说话。

三个候选：

- **(a) 台前内联，不产出结构化对象**——读人块只指导占卜师"心里判断"。零成本，但策略只存在于它说过的话里：十轮后被对话历史稀释，改判无迹可循，无法调试。这就是当前"行为不稳定"的老病根，等于没治。
- **(b) 台前 Agent 通过新工具 `set_reading_strategy` 落单** ✅ **采纳**——读人完成时（通常第 1–2 轮，与澄清同轮）提交六字段策略单，harness 存入会话状态，此后每轮压缩成一行回显注入。改判 = 覆盖调用。判断力仍 100% 留在台前唯一的声音里，没有第二个概率系统；策略跨轮持久、可见、可调试。成本：每个问题一次额外 loop 迭代（与抽牌工具同价），**不是每轮**。
- **(c) 台后每轮小模型导演层**——双概率系统 + 每轮 300–800ms 延迟 + 调试时两个嫌疑人。**否决。**

### 缺口 1：画像卡（含常驻注入）　❌ 未动工

> **2026-08-10 现状**：一行未写。`data/profiles/` 不存在，`context_service` 里没有画像卡相关函数，
> `_build_user_context()`（`gemini_service.py:18`）仍是唯一的用户上下文来源且仍只有那四项，
> `read_divination_notebook` 的工具描述也未改写（仍在承担"记住用户"的职责）。
> 下面的实现方案未过时，可直接照做。

**现状**：`gemini_service._build_user_context()` 只拼昵称/性别/生日/出生地；历史记忆必须靠模型主动调 `read_divination_notebook` 才拿得到——**"被记住"这个核心卖点是概率事件**。

**实现**
- 新数据结构 `data/profiles/{user_id}.json`（沿用 notebook 的 JSON 单文件模式，不引入新存储）。字段：
  - 基本信息：昵称 / 性别 / 出生信息 / 出生地（现有四项）+ 职业 / MBTI / 感情状态
  - 重大生活事件
  - 核心议题及复现次数
  - 近期重复牌面
  - 上次会话一句话摘要
  - 禁区话题
  - **全部事实型，无任何判词**
- 新增 `services/context_service.py`：读画像卡 → 渲染文本块。
- `_format_messages_for_gemini()` 中，`_build_user_context()` 调用替换为 `context_service.build_profile_card()`（现有四字段是其子集，向后兼容），**每轮无条件注入**。
- `read_divination_notebook` 保留，工具描述改为"查看某次占卜的完整原文"，不再承担"记住用户"的职责。
- 硬限长 500 tokens。

**影响**
- ✅ "被记住"从概率变确定——四个痛点中收益最大的一项。
- ✅ 省掉大部分 `read_divination_notebook` 调用 = 每次少一轮 loop 迭代（一次完整 API 往返），**延迟与 token 双双净减**。
- ⚠️ 每轮固定 +300–500 tokens 输入；与省下的 loop 相比仍净赚。
- ⚠️ 画像卡质量直接决定解读质量，写脏会污染每一轮 → 靠硬限长 + 记忆 Agent 侧采集边界约束。
- 前端零改动。

### 缺口 2：接场块　✅ 已实现（换了方案）

> **2026-08-10 现状**：目的达成，方案不同。`stage_greeting.md` **从未创建**——开场白改由前置占卜师
> Agent 真实 LLM 生成（`opening_service.build_greeting()`，8s 超时 + 模板降级），
> 认人靠 `context_service.render_relationship_block()` 注入的关系元数据（昵称 / 来访次数 / 距上次天数），
> 新客与回头客两种变体，"禁止主动翻旧话题"写在块内。详见前置 Agent 设计文档。
> 联调实测：回头客拿到"又见到你了。坐吧，茶刚泡好。"——熟人语气成立且未提旧事。

**现状**：首轮对所有人说同一句欢迎语。

**实现**
- 新提示词文件 `stage_greeting.md`，登记进 `PROMPT_REGISTRY`（管理页可在线编辑）。
- `context_service` 判定：`len(messages) == 0` 且画像卡存在 → 回头客变体（熟人语气、叫昵称、可用代码算出的"距上次 N 天"事实、**明令禁止主动翻旧话题**）；无画像卡 → 新客变体（沿用现有欢迎语调）。
- 非首轮不注入。
- 内容边界由 harness 定义，**具体文案由项目方撰写**。

**影响**
- ✅ 老用户开场不再被当陌生人——关系感最便宜的一次兑现。
- ⚠️ 仅首轮 +约 200 tokens，其余轮次为零。
- ⚠️ 风险：画像卡就在上下文里，模型可能忍不住翻旧账 → 靠块内明令压住，联调重点验证项。
- 前端零改动。

### 缺口 3：读人块 + 牌阵选型　✅ 已实现（换了方案）

**现状**：只有"意图模糊时优先澄清"一句；牌阵选择只有"你来决定"，**无任何选型依据**。

  - **澄清预算：最多 1 轮**；措辞已清晰则零澄清直接进仪式

  - **分类结论绝不外露给用户**

**影响**
- ✅ 补上"读人先于读牌"这个最大产品断层；牌阵从随机决定变为策略的物化。
- ⚠️ 未设策略的轮次 +约 500 tokens；设定后每轮仅 +约 50 tokens 回显。
- ⚠️ **每个问题的首轮多一次 loop 迭代**（调工具 → 返回 ok → 再出文本），首字延迟增加约一次 API 往返。这是本方案唯一的延迟成本，**每个问题只付一次，不是每轮**。
- 前端零改动。

### 缺口 4：`set_reading_strategy` 工具　✅ 已实现（定名 `submit_reading_brief`）

### 5.4 已落地部分的已知缺陷（2026-08-10 首次真实联调）

主链路成立：开场白 → 读人 → 交单落库 → 同轮移交 → 抽牌全程跑通，`phase` 正确翻转，
九字段策略单落库；零澄清路径、催抽牌立刻交单、回头客不翻旧账、开场白无 AI 感（4 句各不相同、
无菜单罗列、无 emoji）均实测通过。以下两项未达设计意图：

**缺陷 1：`reading_strategy` 取值 3/4 非法。** 合法值只有 验证式 / 决策式 / 探索式，实测四份策略单里
三份填成了 `user_goal` 的值（"看清现状"），其中一份连 schema 描述里的括号原文都抄了进去
（"看清现状（迷雾中，要一张地图）"）。根因：`services/llm/tools.py` 的 `reading_strategy`
没有 `enum` 约束，而其 description 写成"验证式（求认同）/ 决策式（辅助决策）/ 探索式（看清现状、探索好奇）"，
括号里列的正是 goal 名，模型直接照抄括号内容。后果是 `render_brief_block()` 往解读提示词注入
"解读策略：看清现状"——**"读人结论指导解读"这个核心机制约 3/4 概率空转**。
修法：加 `enum` 锁死取值，把括号里的对应关系挪到 `opening_system.md` 当说明。

**缺陷 2：高情绪路径 3/3 首轮直奔抽牌，且"问了问题不等回答"。** 设计写的是"情绪浓度高 →
允许第 2 轮纯共情（只陪，不推进任务）"。实测输入崩溃向文本三次，全部首轮就交单 + 首轮就抽
十张凯尔特十字。模型的**判断是对的**（`emotional_intensity=高`、`pacing=深` 都填对），
但那一轮共情从未发生。副作用更难看：前置 Agent 允许在"输出提问文本"的同一轮里交单，
同轮移交随即把解读 Agent 的话续在后面，用户收到的是一条"先共情 → 问一个问题 → 自己往下讲 → 抽牌"
的消息，问题永远不会被等待回答，两个 Agent 的声音粘在同一个气泡里。
缺的是一条约束：**输出了提问就不该同轮交单**。

**附带观察：守卫第 2 层（`mode=ANY` 强制交单）在正常运行下不可达。** 提示词纪律是"绝不超过 2 轮"，
而 `OPENING_FORCE_BRIEF_AFTER_USER_MSGS` 配的是 3——模型在第 2 轮就自己交单了。
好消息是纪律确实生效，代价是这个最高风险的机械兜底至今没被真实跑过；
要验须临时把阈值调成 1 单独测。

## 6. 待确认项

三项都属未实现的 P1 / P3，仍然开放。第 1 项已可用实现期获得的事实收敛：

1. **画像卡的存储形态**：原本纠结"独立 JSON vs users 表加列"。实测 `users` 与 `conversations`
   **都是文档型表**（`data TEXT` 存整个对象 JSON，其余列只是索引影子），所以"加列"并不是自然选项——
   给 Pydantic `User` 加字段即可（`phase`/`strategy` 已验证这条路零迁移），
   而按画像字段筛选/统计用 `json_extract` 就能做（`build_relationship_meta()` 已经这么查 session_type）。
   **倾向：直接进 `User` 模型，不新建 `data/profiles/` 目录，也不加列。**
2. 长会话的画像卡兜底更新频率（暂定每 12 轮用户消息）。
3. 关系环的呈现位置（主界面 vs 旧会话窗口）——P3 细化。
