## 1. 背景与动机

当前占卜核心是**单 Agent + 一组提示词**：一个 Gemini Function Calling Agent Loop 承担全部职责（意图识别、澄清、抽牌、星盘、解读、记忆读取）。四个痛点：

1. **关键行为不稳定**——"读笔记本""控制节奏""从虚到实"这些核心设计全靠提示词祈使句，模型时灵时不灵。
2. **提示词过载**——人格、流程、工具、风格混在一个大文件里互相干扰，function calling 准确率被拖累。
3. **新能力塞不下**——实时用户画像、主动问候/每日推送，在单 Agent 架构里无处安放。
4. **记忆能力设计不足**——长期记忆依赖模型主动调工具，是概率事件而非确定行为。

本文档先定义**产品要做什么**（第 2 节），再定义**技术怎么做**（第 3–5 节）。

## 2. 产品层重构（要做什么）

### 2.1 现有工作流拆解

把一场占卜按用户经历的顺序解剖，现状是：

| 幕 | 现在发生什么 | 设计状态 |
|---|---|---|
| ① 进场 | 通用欢迎语，邀请提问 | **空白**——对第 1 次和第 10 次来的人说同一句话 |
| ② 提问 | 预输入（硬编码）或自由输入 | 已设计，不动 |
| ③ 澄清 | 提示词一句"意图模糊时优先澄清" | **半设计**——只澄清"问题"，不读"人" |
| ④ 仪式 | AI 决定牌阵 → 按钮 → 洗牌 → 扇形选牌 | 已设计，产品亮点，不动 |
| ⑤ 解读 | 牌义 → 个性化 → 投射提问 → 叙事串联，从虚到实 | 理念完整，执行靠自觉 |
| ⑥ 反馈 | "解读是否偏离""你想到了哪件事" | 有设计，但反馈信号用完即弃 |
| ⑦ 收尾 | 不存在，对话默默衰减 | **空白** |
| ⑧ 离场后 | 12 小时后定时生成笔记 | 纯归档，用户无感知 |
| ⑨ 回访 | 与新用户零差别 | **空白** |

**结论：会话中段（②④⑤）精心设计，两端（①③⑦⑧⑨）接近裸奔。** 而两端决定关系——产品愿景是"个人专属的情感陪伴"，但当前工作流本质是**单场服务模型**：一锤子买卖做得精致，买卖之间没有关系。

### 2.2 三个视角的断层诊断

**占卜师视角——"读人先于读牌"缺失。** 真实占卜师在洗牌前已完成一半工作：判断来人是求确认还是真迷茫。README 已写出这个洞察（四类用户目标：已有答案求认同 / 辅助决策找理由 / 探索好奇 / 玄学目的，且"目标会在占卜中变化"），**但当前工作流对这个分类零使用**。同一张"恋人逆位"，对求认同者和对找决策理由者，正确策略完全不同。这个判断现在完全悬空。

**心理从业者视角——会谈没有弧线。** 咨询每一节都有结构：开场衔接 → 中段工作 → 收尾整合。用户记住一场体验的方式由峰值与结束决定（峰终定律）；峰值有设计（被命中的瞬间、抽牌仪式），结束是真空。

**C 端产品视角——留存环是断的。** 陪伴型产品的环应是：会话 → 记忆沉淀 → 回访钩子 → 回访触发 → 衔接开场 → 会话。现在五段断了三段：沉淀延迟 12 小时且不保证被使用、回访钩子从未制造、回访触发不存在。**每次回来都要重新自我介绍的产品，谈不上情感依赖。**

### 2.3 重构后的产品定义

从"一场精致的占卜"升级为"**一段被经营的占卜关系**"。

**会话内四幕：**

1. **接场**——认人但不翻旧账。老用户用熟人语气、叫昵称，**不主动提旧话题**（旧话题属于关系环，不侵入新会话）；新用户走现有欢迎引导。
2. **定义占卜**——暗活，用户不可见。把问题问到能起卦，决定用塔罗还是星盘、用什么牌阵，产出**本场起手单**。追问预算**最多 1 轮**。
   *（原案此处写的是"读人"——在澄清的同时判断用户目标与情绪浓度。该判断已于 2026-09-15 从开场幕撤销，
   命题本身仍然成立，但改由缺口 1 的画像卡以长期观察承担，理由见缺口 3。）*
3. **仪式**——现有抽牌流程**原样保留**。
4. **解读**——现有方法论**原样保留**（从虚到实、投射提问、叙事串联、多次抽牌纪律）。

**离场工序（不可见）：** 会话退出/静默超时后，记忆沉淀 + 钩子提取。

> **收尾幕已评估并撤销**：它的三个价值中，回访钩子可由离场工序从对话原文提取（无需台前说出），整合已包含在现有解读收束话术中，而峰终记忆依赖"准确识别用户要走了"——该判断天然不可靠，误判提前收束等于赶客。**不做结束判断、不加结束按钮。**

**关系环（本期只出 spec，不实现）：** 离场 → 记忆沉淀（含钩子）→ 回访触发（主界面或旧会话窗口的主动接话）→ 下一场。

### 2.4 已对齐的产品决策

- **人格 ≠ 功能**。塔罗 / 占星是**功能**（同一个 Agent 都会，入口只决定起手优先级）；人格是同一占卜师的口吻风格变体（温柔型 / 直接型）。README 描述的双人格**在代码中并不存在**——两份提示词的实质差异只有工具优先级顺序。**本期人格单一，结构上留出替换位置。**
- **反馈沉淀只沉淀事实，不沉淀判词**。沉淀 MBTI、职业、感情状态、重大事件等客观画像；**绝不沉淀"准/不准"判词**。用户说"不准"是本场对话内的信号，由解读方法论当场处理（探索落差、坚持牌面立场），**不能因单次反馈就长期扭转话术**——那是占卜方法论的自毁。

## 3. 技术层设计（怎么做）

### 3.1 总体原则

- **纯增量**。现有 `tarot_system.md` / `astrology_system.md` **一字不动，本期不做去重**（两份文件的方法论重复是已知负债，列为后续优化）。所有新增能力以**追加块**形式由 harness 拼装在现有系统提示词之外。
  *（实际落地时此条部分改变：解读相位仍是追加块，但开场相位用的是一份完整独立的
  `opening_system.md`，不叠在塔罗提示词上。两份大提示词本身确实一字未动，去重也确实没做。
  代价是它们里"首次对话先欢迎""参数化澄清"两条指令与开场幕打架，需另注入接场约束压掉——见缺口 2。）*
- **单一台前声音**。只有占卜师 Agent 对用户说话。不引入台前导演层（每轮串行小模型判断）——双概率系统 + 每轮延迟，收益不抵成本。
- **判断力留在台前，产物落到后台**。策略判断由占卜师自己做（它有全部上下文），但产出必须是结构化对象并持久化，而非散落在对话历史里。
- **台后异步**。记忆沉淀不占用户等待时间。
- **不实现**：危机正则、情绪优先铁律、提示词去重、双人格、收尾幕。

### 3.3 核心决策：策略单由谁产出（保留为决策记录；实际走了第四条路）

当时的三个候选与结论如下。**实际实现走的是 (b) 的变体**：策略单仍由台前 Agent 经工具落单
（所以 (a)/(c) 的否决理由依然成立），但读人不再由那个"唯一台前 Agent"兼任，
而是拆给一个独立的前置 Agent，用自己的小提示词做完再移交——即分幕接力。
被否决的 (c) 与此有本质区别：(c) 是每轮都跑第二个模型，分幕接力是每场只在开场跑一次，
任意时刻仍只有一个声音在说话。

三个候选：

- **(a) 台前内联，不产出结构化对象**——读人块只指导占卜师"心里判断"。零成本，但策略只存在于它说过的话里：十轮后被对话历史稀释，改判无迹可循，无法调试。这就是当前"行为不稳定"的老病根，等于没治。
- **(b) 台前 Agent 通过新工具落单** ✅ **采纳**——判断完成时经工具提交结构化单子，harness 存入会话状态，此后压缩成一行回显注入。判断力仍 100% 留在台前唯一的声音里，没有第二个概率系统；单子跨轮持久、可见、可调试。成本：每场一次额外 loop 迭代（与抽牌工具同价），**不是每轮**。
  *（工具最终定名 `submit_reading_brief`；原案设想的"改判 = 覆盖调用"未实现——见缺口 4 第 3 条，起手单是一次性记录。）*
- **(c) 台后每轮小模型导演层**——双概率系统 + 每轮 300–800ms 延迟 + 调试时两个嫌疑人。**否决。**

### 缺口 1：画像卡（含常驻注入）　❌ 未动工

> **2026-09-15 现状**：一行未写。`context_service` 里没有画像卡相关函数，
> `_build_user_context()`（`gemini_service.py:18`）仍是唯一的用户上下文来源且仍只有那四项，
> `read_divination_notebook` 的工具描述也未改写（仍在承担"记住用户"的职责）。
> 下面的实现方案未过时，可直接照做——**但存储形态按 §6 第 1 项的结论走**（进 `User` 模型）。

**现状**：`gemini_service._build_user_context()` 只拼昵称/性别/生日/出生地；历史记忆必须靠模型主动调 `read_divination_notebook` 才拿得到——**"被记住"这个核心卖点是概率事件**。

**实现**
- 画像卡字段进 Pydantic `User` 模型（§6 第 1 项的结论，取代原案的 `data/profiles/{user_id}.json`）。字段：
  - 基本信息：昵称 / 性别 / 出生信息 / 出生地（现有四项）+ 职业 / MBTI / 感情状态
  - 重大生活事件
  - 核心议题及复现次数
  - 近期重复牌面
  - 上次会话一句话摘要
  - 禁区话题
  - **全部事实型，无任何判词**
- 新增 `services/context_service.py`：读画像卡 → 渲染文本块。
- `_format_messages_for_gemini()` 中，`_build_user_context()` 调用替换为 `context_service.build_profile_card()`（现有四字段是其子集，向后兼容），**每轮无条件注入**。
- `read_divination_notebook` 保留，工具描述改为"查看某次占卜的完整原文"，不再承担"记住用户"的职责。
- 硬限长 500 tokens。

**影响**
- ✅ "被记住"从概率变确定——四个痛点中收益最大的一项。
- ✅ 省掉大部分 `read_divination_notebook` 调用 = 每次少一轮 loop 迭代（一次完整 API 往返），**延迟与 token 双双净减**。
- ⚠️ 每轮固定 +300–500 tokens 输入；与省下的 loop 相比仍净赚。
- ⚠️ 画像卡质量直接决定解读质量，写脏会污染每一轮 → 靠硬限长 + 记忆 Agent 侧采集边界约束。
- 前端零改动。

### 缺口 2：接场（认人不翻旧账）　✅ 已实现

**原问题**：首轮对所有人说同一句硬编码欢迎语，第 1 次和第 10 次来的人待遇相同。

**实际落地**（原案的 `stage_greeting.md` 提示词块从未创建，改由前置 Agent 承担）：
开场白走真实 LLM 调用（`opening_service.build_greeting()`，8s 超时 + 模板降级）；
认人只靠 `context_service.render_relationship_block()` 注入的三项事实——称呼 / 第几次来访 / 距上次多少天；
新客与回头客的语气差异、"禁止主动翻旧话题"的禁令都写在 `opening_system.md` 里（管理页可在线改），
代码里不藏文案。**不依赖画像卡**：熟人感来自语气，不来自复述档案。

详见 [前置占卜师 Agent 设计 §8–§9](2026-07-14-opening-agent-design.md)。
联调实测：回头客拿到"又见到你了。坐吧，茶刚泡好。"——熟人语气成立且未提旧事。

### 缺口 3：读人 + 牌阵选型　⚠️ 只落地了牌阵选型；读人已撤销

**原问题**：只有"意图模糊时优先澄清"一句；牌阵选择只有"你来决定"，**无任何选型依据**。

**实际落地**（原案的 `stage_reading_person.md` 从未创建，内容进了 `opening_system.md`）：

- ✅ **牌阵选型表**（问题类型 → 牌阵 → 各位置含义）落地，牌阵从随手一抽变成问题的物化。
- ✅ **叙事性澄清**取代参数化填表，追问预算最多 1 轮，措辞已清晰则 0 轮直接交单。
- ❌ **读人被删除**：四类用户目标措辞判据、情绪浓度、三种解读策略在 2026-09-15 全部从提示词与起手单里移除。
  前置 Agent 现在不产出任何关于人的判词。

**为什么撤销**：这三项判词是 §5.4 两个缺陷的共同根因（判词字段互相抄串、"高情绪先共情"与"读人完成即交单"同轮打架），
而且一旦开场要给人定性，塔罗与星盘就在开场分成两条产品线。详见
[前置占卜师 Agent 设计 §2.1](2026-07-14-opening-agent-design.md)。

**"读人"这个产品命题本身没有被否定**——README 里"同一张牌对求认同者和对找决策理由者策略不同"的洞察依然成立。
被否定的只是"让前置 Agent 在开场用一次性判词把人定性"这条实现路径。
真要做，正确的载体是**画像卡的长期观察**（缺口 1），不是开场三十秒的一次抽样。

### 缺口 4：起手单工具　✅ 已实现（定名 `submit_reading_brief`）

**原问题**：策略判断悬空，只存在于模型说过的话里，十轮后被对话历史稀释，无法调试。

**实际落地**——工具定名 `submit_reading_brief`，**六字段**：
`question` / `context` / `route` / `spread_type` / `card_count` / `positions`（必填 `question` + `route`，后者 `enum` 锁死）。
规格集中在 `services/llm/tools.py`（缺口 7 重构后的唯一真源）。

四处与原案不同，以实际为准：

1. **没有加 SQL 列。** `conversations` 表是文档型存储（整对象 JSON 在 `data` 列），
   给 Pydantic `Conversation` 加 `strategy` / `phase` 两个字段即可，零迁移、零回填脚本
   （存量会话反序列化自动补 `phase="reading"`，确定性路由到解读 Agent）。
2. **加了显式相位状态位 `phase` 与三层守卫**（提示词纪律 / 强制工具调用 / harness 兜底翻相位），
   保证数学上不存在卡死在开场幕的会话。
3. **起手单不可改判。** 解读工具集里没有 `submit_reading_brief`——它是开场定下的一次性记录，
   不是可覆盖的当前状态。中途换角度、补抽牌阵由解读 Agent 自理。
4. **交单后分两条路线**：塔罗由 harness 照单直推抽牌器（零额外往返）；星盘同轮移交解读 Agent 自己取盘。

字段不产生 SSE 前端事件（纯后台工具）。后台管理页可查看每场的起手单卡片。
详见 [前置占卜师 Agent 设计 §4–§6](2026-07-14-opening-agent-design.md)。

**剩余风险**：依赖模型愿意调该工具，function calling 准确率是本项主要风险——
守卫第 2 层（强制工具调用）是兜底，但它在非 Gemini provider 上的支持度尚未验证（见缺口 7）。

**现状**：`notebook_system.md` 只产出 `{summary, cards_drawn}`，退出后 12 小时由定时器触发，纯归档。

**实现**
- 提示词扩为三产物：
  1. **会话档案**（现有格式不动）
  2. **画像卡增量更新**——本场新出现的事实；明确采集边界；明确禁止项（不写"准/不准"判词、不写风格推断）
  3. **钩子提取**——未完结话题一句话 + 日期（本期只落库，不消费）
- `notebook_task_scheduler`：触发时机从"退出后 12 小时"改为"**最后消息后 30 分钟未续**"；长会话每 12 轮用户消息追加一次增量更新兜底。
- 新增一次性**存量迁移脚本**：老用户历史笔记本 → 初版画像卡（否则新架构上线当天，所有老用户在系统眼里都是新人）。
- 画像卡更新采用**重写而非追加**语义，控制膨胀漂移。

**影响**
- ✅ 离场工序确定发生，画像持续生长；钩子为关系环备料。
- ✅ 沉淀提前（12h → 30min），用户当天回访即可享受更新后的画像。
- ⚠️ 每场会话一次 flash-lite 调用，异步执行，用户无感知；成本可忽略。
- ⚠️ 画像卡是累积结构，长期有膨胀与漂移风险 → 硬限长 + 重写语义 + 采集边界三重约束。

### 缺口 7：三 Agent 独立 provider　⚠️ 代码完成，未验证

**探索期未识别，实现期临时插入**（2026-07-15）。详见

tool_call 参数格式、`tool_choice`（守卫第 2 层所依赖）支持度在 mock 下看不见。

**且这已不是待启用的开关**：根 `.env` 三个 Agent 现均配置为 `deepseek`（模型 `deepseek-flash`），
多 provider 路径就是当前实际运行路径。因此 `backend/scripts/check_providers.py` 的四项检查

不是可选的预验证，而是当前线上行为的直接依据——**换 provider 或换 model 之后都应重跑**。

### 5.4 已落地部分的已知缺陷（2026-08-10 首次真实联调 → 2026-09-15 已修）

首次联调发现两项未达设计意图，两项都在 09-15 的收敛重构里消解了——不是打补丁，是把
产生它们的那部分设计删掉。

**缺陷 1：`reading_strategy` 取值 3/4 非法。** 合法值只有 验证式/决策式/探索式，实测四份策略单
三份填成了 `user_goal` 的值。根因：schema 无 `enum`，而 description 的括号里列的正是 goal 名。
**修法：`reading_strategy` 连同其余判词字段一起从起手单删除**，字段没了，抄袭也就没了。
保留的 `route` 加了 `enum` 锁死。

**缺陷 2：高情绪路径 3/3 首轮直奔抽牌，且"问了问题不等回答"。** 根因是提示词里两条指令
在同一轮同时成立——"情绪浓度高 → 第 2 轮纯共情"要求它说话，"读人完成即交单"要求它交单，
没有任何一句说这俩不能同时做。**修法：删掉共情轮**（陪伴是解读阶段的事，前置 Agent 不承担），
并在提示词里写死"问了问题这一轮就不要交单"。harness 不做特例——模型返回 text + tool_call
就执行工具继续循环，这是标准 agent loop 行为，不该为它加机械拦截。

**守卫第 2 层（`mode=ANY` 强制交单）仍未在真实运行下跑过。** 提示词纪律是追问最多 1 轮，
而 `OPENING_FORCE_BRIEF_AFTER_USER_MSGS=3`，模型总是先自己交单。要验须临时把阈值调成 1。

### 5.5 开场幕收敛重构（2026-09-15）

**动机**：原设计让前置 Agent 同时干两件事——定义占卜（问题/手段/牌阵）和读人（目标/情绪/
解读策略）。后者产出的九字段里有六个是关于人的判词，既是缺陷 1、2 的根因，也让"塔罗会话"
和"占星会话"在开场就分了叉。收敛后前置 Agent 只剩一个职责：**把这场占卜定义清楚。**

| 改动 | 前 | 后 |
|---|---|---|
| 起手单字段 | 九字段（含 user_goal / emotional_intensity / reading_strategy / pacing） | 六字段：question / context / route / spread_type / card_count / positions |
| 开场工具集 | 只有 `submit_reading_brief` | 加 `request_user_profile`——星盘路线要出生信息，它得自己要 |
| 解读工具集 | 含 `submit_reading_brief`（供中途改判） | 移除。起手单是一次性记录，不是可改写的当前状态 |
| 开场提示词上下文 | 关系块 + 入口 | **加 `<用户资料>`**——不注入它，模型看不见用户填没填出生信息，就没法自己判断星盘这条路走不走得通 |
| 塔罗路线交单后 | 同轮移交 → 解读 Agent 说过渡语 + 自己再选一次牌阵 → 抽牌 | **harness 照单直接推抽牌器**，一次 provider 往返，牌阵与单子逐字一致 |
| 星盘路线交单后 | 同左 | 保留同轮移交（不需要用户动手，解读 Agent 取盘后直接开口） |
| 关系块/入口块文案 | 硬编码在 `context_service` | 只注入事实行（`称呼：X ｜ 第 3 次 ｜ 距上次 12 天`），语气指令搬进 `opening_system.md`（管理页可改） |
| 接场约束 | 硬编码 `_HANDOFF_INSTRUCTION` | 抽成 `prompts/reading_handoff.md`，登记 `PROMPT_REGISTRY` |

**塔罗与星盘不再是两条产品线。** 对前置 Agent 来说它们只是手段选项，判断逻辑同一套；
入口只是先验偏好。`route` 填的是**起手动作**，不是全场计划——两个都想用就填先做的那个，
另一个到解读阶段由解读 Agent 自己引入（它工具齐全，不需要回开场幕）。

**代码里还剩的硬编码提示词只有两处**：守卫强制交单那句、开场白降级模板。两者都是
"出事才用"的机械件，不是要反复调的产品文案。

**新增数据兜底**：`context_service.to_plain()` —— `positions` 进入起手单后，proto 的
RepeatedComposite / float 会直接 `json.dumps` 炸在落库那一步，交单参数统一在此收口。

## 6. 待确认项

三项都属未实现的 P1 / P3，仍然开放。第 1 项已可用实现期获得的事实收敛：

1. **画像卡的存储形态**：原本纠结"独立 JSON vs users 表加列"。实测 `users` 与 `conversations`
   **都是文档型表**（`data TEXT` 存整个对象 JSON，其余列只是索引影子），所以"加列"并不是自然选项——
   给 Pydantic `User` 加字段即可（`phase`/`strategy` 已验证这条路零迁移），
   而按画像字段筛选/统计用 `json_extract` 就能做（`build_relationship_meta()` 已经这么查 session_type）。
   **倾向：直接进 `User` 模型，不新建 `data/profiles/` 目录，也不加列。**
2. 长会话的画像卡兜底更新频率（暂定每 12 轮用户消息）。
3. 关系环的呈现位置（主界面 vs 旧会话窗口）——P3 细化。
